# WindowServer / SkyLight: findings

Notes on the private APIs nori uses or could use. Checked on macOS 27 (Darwin 27.0.0), Apple Silicon.
"Verified" = seen with our own eyes; "not verified" = inferred from the disassembler, or a guess.

## How to look

- Payload logs: `/usr/bin/log show --last 1h --predicate 'process == "Dock" AND eventMessage CONTAINS "nori"' --style compact`.
  In zsh plain `log` is a builtin and silently shows nothing. Use the full path `/usr/bin/log`.
- SkyLight exports (it lives in the shared cache, `nm` won't help):
  `dyld_info -exports /System/Library/PrivateFrameworks/SkyLight.framework/SkyLight | awk '{print $NF}' | grep -i <something>`
- Disassembling a SkyLight function without Dock: any binary of our own, `lldb -b ./bin -o "b main" -o run -o 'expr (void*)dlopen("/System/Library/PrivateFrameworks/SkyLight.framework/SkyLight",1)' -o "dis -n <Function>"`.
- Which functions Dock calls during an action: attach to Dock and set auto-continuing breakpoints (with Debugging Restrictions off this works without sudo, and Dock doesn't crash):
  ```
  breakpoint set -n SLSTransactionSetSpaceShape -n SLSTransactionSetSpaceTransform -G1
  breakpoint command add 1
  frame info
  register read x1 x2 x3 d0 d1 d2 d3
  DONE
  process continue
  ```
  `lldb -p $(pgrep -x Dock) -s file.lldb > out &`, then the action (e.g. `osascript -e 'tell application "System Events" to key code 19 using {option down}'`), then `pkill -f "lldb -p"`.
- A window's Space and the active Space from the daemon: `CGSGetActiveSpace(CGSMainConnectionID())`, `CGSCopySpacesForWindows(cid, 7, [wid])` — exported by CoreGraphics, linked from Swift through `@_silgen_name` with no extra flags. Verified.

- Field names and types of Dock's Swift classes: `__TEXT,__swift5_fieldmd`. Xcode 27.1 has no `swift-reflection-dump`, but the records are simple enough for a short script: 16 bytes of header, then 12 per field (flags, relative type name, relative field name). A `\x02` in a type name points through a pointer to a context descriptor, whose name is at +8.

- SkyLight's local symbols, server code included: lldb reads them from the shared cache in any process of ours. `image lookup -r -n <regex> SkyLight`, or `image dump symtab -s address SkyLight` for the whole table (32,000 lines). With that table and the code section (`memory read --force --binary --outfile`) a short script finds every caller of a function. WindowServer's own code is in the same file: `_X…`, `PKG…`, `WS…`, `CGX…`.

- Test code in a running Dock: a stub loaded once with `sudo /usr/local/libexec/nori/loader stub.dylib`, which `dlopen`s paths from a socket of its own, so later builds, each under a new file name, need no password. Not lldb's `process load`: it reached `dlopen` once after 9.6 s, failed twice with "failed executing dlopen wrapper function", and Dock restarted around the third try (no crash report, cause not established). It runs with the other threads stopped, the likely reason for the failures (inferred).

- A test layout has to end on `SLSGetActiveSpace`, asked at that moment. One ending on a fixed Space left the current Space hidden after the Space had changed meanwhile, and the screen showed another Desktop's windows until a frame showed the current one again. Seen once.

- A login's id: `CGSSessionUniqueSessionUUID` in `CGSessionCopyCurrentDictionary()`. A Space's `uuid` in `CGSCopyManagedDisplaySpaces` is the one in `com.apple.spaces` (`SpacesDisplayConfiguration`), which is why nori keeps a strip across a reboot under it; that both change or last as expected over a real reboot is not verified.

## Space switching in Dock

Verified with the hook log and lldb. Dock does the switch (Ctrl/Option+N, swipe) itself, frame by frame, about every 16 ms (60 Hz), around 15 frames per switch:

1. `SLSTransactionWillSwitchSpaces`
2. `SLSTransactionShowSpace` for the new Space
3. every frame, for the old and the new Space:
   - `SLSTransactionSetSpaceTransform(transaction, sid, u32 = 4, const CGAffineTransform *)` — a pure translation, `tx` going smoothly from 0 to ±display width in pixels (3072 on this screen); neighbouring Spaces are offset by ±3072.
   - `SLSTransactionSetSpaceShape(transaction, sid, CGRegionRef)` — the Space's clip, a new region every frame. This is what gives the black band when the transform is made vertical but the clip stays horizontal.
   - `SLSTransactionSetSafeApertureSpaceReveal(transaction, sid, d0 = progress 0…1, …)` — something about the notch area (safe aperture). Not explored.
4. In the transaction of the last frame, in this order (traced with timestamps, all within about 10 ms): `SLSTransactionHideSpace` for the old Space, that frame's transforms, `SLSTransactionSetManagedDisplayCurrentSpace`, which comes last among these. `SLSTransactionSetSpaceOrderingWeight` was logged too; its place wasn't traced.

A Space transform is 2D affine only: translation and scale work (that's how Mission Control works), perspective does not.
Verified with the disassembler: `SLSTransactionSetSpaceTransform` reads exactly 6 doubles from the pointer (CGAffineTransform); the `u32` is passed as a separate number (a flag, meaning unknown). `SLSSpaceSetTransform` also takes 2D (two q registers = 4 doubles + tx/ty). SkyLight has no exports like `Space…3D` / `Space…Warp`.
`SLSSetSessionSwitchCubeAnimation(bool)` — only the "cube on fast user switching" flag, sent to the server root port. Useless for Spaces.
Conclusion: 3D for a Space only works through its windows — `SetWindowTransform3D` on every window of both Spaces (wallpapers are windows too).

The hook in `payload/payload.m` (`hook`) patches the first 16 bytes of the function in Dock's copy of SkyLight (a jump to our stub; the stub swaps the argument and runs the displaced prologue). Verified for `SLSTransactionSetSpaceTransform`: the horizontal shift becomes vertical, the log says `… hooked (kr=0)`.
Prologues on macOS 27 (both free of PC-relative instructions, so they can be copied into the stub):
- `SLSTransactionSetSpaceTransform`: `pacibsp; stp d9,d8,[sp,#-0x40]!; stp x22,x21,[sp,#0x10]; stp x20,x19,[sp,#0x20]`
- `SLSTransactionSetSpaceShape`: `pacibsp; sub sp,sp,#0x50; stp x22,x21,[sp,#0x20]; stp x20,x19,[sp,#0x30]` (`d503237f d10143ff a90257f6 a9034ff4`)

The `SetSpaceShape` hook turns the slide's horizontal clip vertical: it takes the region's bounding box and maps its x range to y with an H/W factor, like the transform. This should remove the black band. **Not verified**: which coordinates the region is in (screen, or the Space before its transform); so far only an assumption that they match the transform.

The hooks work only while the daemon is alive: the daemon sends `P <pid>` every 2 s, and the hook checks `kill(pid, 0)`. Once the daemon exits or crashes, Dock animates by itself again. The patch itself stays until Dock restarts.

A layout (the overview, a slide) never ends by itself at goal 1, so a crash used to leave Spaces scaled until Dock restarted. `close_orphan_layout` checks the same `kill(pid, 0)` every frame of a layout: with the daemon gone it lets go of any swipe, sets goal 0 and aims at `SLSGetActiveSpace`, asked again each frame as a switch of Dock's may land after the crash, and `step_layout` ends the layout as usual. `instant` ("I 1") has no effect with the daemon gone, the hooks ask first, but it would come back with the next daemon, so a new pid in `P` clears it.

Signatures (disassembler; the arguments are visible in lldb during a switch):
- `SLSTransactionShowSpace(transaction, sid)`, `SLSTransactionHideSpace(transaction, sid)` — 2 arguments each.
- `SLSTransactionSetSpaceShape(transaction, sid, CGRegionRef)`. Dock gives a hidden Space `kCGRegionEmptyRegion`.
- `SLSTransactionSetSpaceOrderingWeight(transaction, sid, int)` — Dock sets 1 on the new one and 0 on the old one.
- Regions: `CGRegionCreateWithRect(CGRect)`, `CGRegionIsEmpty`, `CGSGetRegionBounds(region, CGRect *)` are exported by CoreGraphics.
- `CGSCopyManagedDisplaySpaces(cid)` (links from Swift without SkyLight): an array of displays, each with `"Spaces"` (`id64`, `ManagedSpaceID`, `type`: 0 desktop, 4 fullscreen) and `"Current Space"`. Verified.
- Display 3008×1692 pt, Dock's slide is 3072: Spaces sit 64 pt apart, a Space transform is in points. Direction: Dock gives a Space leaving to the right `tx = −3072`, so a Space transform, like a window's, maps screen → Space.

## System Space shortcuts

"Switch to Desktop 1…N" — `com.apple.symbolichotkeys`, keys 118, 119, 120, 121, 122 (desktops 1–5). Parameters `(character, keycode, modifiers)`, Option = 524288, Ctrl = 262144. Keycodes of digits 1–5 on the US layout: 18, 19, 20, 21, 23.
Turning them on without the UI: `defaults write com.apple.symbolichotkeys AppleSymbolicHotKeys -dict-add 118 '<dict>…</dict>'`, then `/System/Library/PrivateFrameworks/SystemAdministration.framework/Resources/activateSettings -u`.
Verified on macOS 27 (Darwin 27.0.0), on keys of a Desktop that doesn't exist: the preferences change at once, and a running process sees that within 50 ms; `CGSIsSymbolicHotKeyEnabled` stays false until `activateSettings -u`, which takes about 0.5 s and has applied it when it returns. Several pairs in one `-dict-add` work, and going back to the old value left `defaults export` identical. Not tried: a real press of a shortcut turned on this way.
What WindowServer has is what counts, and it differs from the preferences in two ways. A preference alone does nothing until applied. And a key missing from the preferences still has keys: `CGSGetSymbolicHotKeyValue(id, &character, &keycode, &flags)` gives macOS's default, disabled, for one never set (127 Ctrl+0; 128–133 Ctrl+Option+1…6, flags 786432). That is the normal case: the new-account template (`/System/Library/Templates/Data/Library/User Template/English.lproj/Library/Preferences/com.apple.symbolichotkeys.plist`) has none of 79–82 or 118–133. So nori reads both calls, from CoreGraphics, and writes the keys it read when it turns one on. "Move left/right a space" (79, 81) defaults to on in macOS (from memory, a new account wasn't tried), so going by the preferences would have called them off. 80 and 82 are the same two with Shift, and nori doesn't use them.

## Windows

- Moving (`SLSMoveWindowWithGroup` / transactions, even from Dock) is clamped by WindowServer to the screen edge. Verified: a window sent to y = 3000 landed at y = 1541 (part of it stayed on screen); sent to y = −3000 it landed at y = 0. A window can't be hidden off screen by moving it.
- `SLSSetWindowTransform(cid, wid, CGAffineTransform)` — 2D. The matrix is inverted (screen → window), as in yabai. Not rechecked.
- **`SLSTransactionSetWindowTransform3D(transaction, wid, const double m[16])`** — a 4×4 window transform (CATransform3D layout, 16 doubles in a row). Signature from the disassembler: `x0` transaction, `w1` wid, `x2` pointer, offsets 0x00…0x78 are read. In the payload: the `D wid m11 … m44` command.
  Verified on a live window (Dock, macOS 27):
  - The matrix is **inverted**: screen point → window point. `m41=300, m42=150` shifts the window 300 left and 150 up; `m11=m22=2` shrinks the window by half.
  - Units are points. The origin is the window's **top-left corner** (scaling shrinks the window towards that corner).
  - Row convention, as in CATransform3D: `x_window = x·m11 + y·m21 + m41`, `y_window = x·m12 + y·m22 + m42`, `w = x·m14 + y·m24 + m44`.
  - Screen points lie at z=0, so `m34` does nothing. Perspective goes through `m14/m24`, i.e. it is a 2D homography. Recipe: build the forward homography H (3×3, columns, window-local coordinates → screen), take G = H⁻¹, normalize by G[2][2] and lay it out: `m11,m21,m41 = G[0]`, `m12,m22,m42 = G[1]`, `m14,m24,m44 = G[2]`, `m33 = 1`.
  - Rotation about the vertical axis through the window's center with perspective (θ = ±0.6, d = 1500) works: a live window in 3D, drawn even outside its bounds. Script: H = T(c)·P·T(−c), P = `[[cos θ,0,0],[0,1,0],[sin θ/d,0,1]]`.
  - The identity matrix puts the window back as it was.
- `SLSSetWindowWarp` / `SLSTransactionSetWindowWarp` — mesh warp of a window (the genie effect). Not verified.
- `SLSSetSessionSwitchCubeAnimation` — the fast-user-switching cube. Not explored.
- Also available: `SLSSetWindowTransforms` (batched), `SLSTransactionSetSpaceAlpha`, `SLSCreateGenieWindowAnimation`, `SLSSetWindowAnimationProgress`, `SLSAddWindowFilter` / `SLSNewCIFilterByName` (CI filters on windows).
- **WindowServer notifications do reach a plain process (macOS 27.0).** `SLSRegisterConnectionNotifyProc(SLSMainConnectionID(), handler, 1325, NULL)` and the same for 1326, in an accessory `NSApplication` with `app.run()` going: a borderless panel of a separate process gave 1325 as it opened and 1326 as its process exited, on the main thread, each 12 bytes: the Space id (64 bits), then the window id (32). Verified with a probe. Sunlight's source names 1325 a window added to a Space and 1326 one leaving it, closed, minimized, hidden or moved (from its comments, the last three not tried here). An earlier probe of every type 100…2000, with and without `NSApplicationLoad()`, saw no callback at all and concluded the opposite; not traced why, a run loop that never ran is the likely reason (inferred). `daemon/Events.swift` runs a poll on them, beside its Accessibility observers per app and NSWorkspace notifications. Menus and tooltips come through too: a new window at a level other than 0 (`SLSGetWindowLevel`) runs no poll, and neither does a window leaving that nori never listed.
- **`CGWindowListCopyWindowInfo` reports window bounds after the Space transform.** Verified: with the overview open (scale 0.4) a 1512×1567 window at (748, 40) was listed as 692×188 at (1158, 825), and windows of the other shown Spaces became "on screen" with negative y. While a Space has a transform, CGWindowList frames can't be trusted: the daemon's strip keeps the frames from its last normal poll then (`syncColumns`, `spaceLayoutBusy`). Otherwise windows really move and shrink (the resize took its width from such a frame).
- `CGWindowListCopyWindowInfo` with `.optionOnScreenOnly` shows only windows of the current Space; a window on another Space may have bounds (0, 0) in `.optionAll`.
- **An Accessibility resize stops at the bottom of the screen, going by the position the app knows, not the real one.** Verified on macOS 27, with a plain `NSWindow`: a window opened at y 450 and being moved to y 50 by the payload took height 1156 of the 1541 asked for, though `AXSize` returned success and the window has no size limits; the same window opened at y 60 took 1541. Lookout (GPUI), opened at y 450, stuck at the same 1156 and took 1541 once `AXPosition` read y 50. The limit looks like the visible frame's bottom, 1607 here (inferred from 450 + 1156, off by one). The app learns of payload moves late if at all: `AXPosition` gave x 2968 for a window WindowServer had at x 3819. So `AXPosition` goes before `AXSize`, and again after it for apps that move a window as it grows (`setFrame`, `daemon/Windows.swift`). Coming back from floating goes the same way.
- **The same goes for the right edge of the screen.** Verified on macOS 27 with a plain `NSWindow` 1620 wide on a 3008 pt screen: at x 694, `AXSize` 2960 took 2314 and 2400 took 2314 too, as 694 + 2314 = 3008; at x 200, 2960 took 2808; at x 24 it took 2960, and so did `AXPosition` 24 before `AXSize` at x 694. That was "toggle-full-width" landing at about 78% after a stretch to the full width: the real window stays at its old place under the stretch. The move has to come from the app's own idea of where it is, and AXPosition moves the real window, so the payload puts it at its final left edge once the stretch has settled, with the same picture (drawn `cx − d/2` to `cx + d/2` either way), and `AXPosition` then moves nothing. The AX numbers are measured, the payload's part isn't yet.
- **Accessibility doesn't lag a Space change.** Measured every 10 ms over a switch both ways: an app's `AXWindows` changes to the new Space's windows within about 20 ms of `CGSGetActiveSpace`, usually before it. An app that doesn't answer within the 0.25 s timeout is a different matter: it returns `kAXErrorCannotComplete` (-25204), seen from one app for a whole 7 s run.

### Windows of our own, through SkyLight only

Prototyped from a plain process (macOS 27) for window borders, which were then dropped. CoreGraphics exports the same calls as `CGS…` (`CGSNewWindow`, `CGWindowContextCreate`, …), so Swift needs no SkyLight:
- `SLSNewWindow(cid, 2, x, y, region, &wid)`: `2` buffered, `region` the shape in window coordinates (`CGRegionCreateWithRect(0, 0, w, h)`), `x, y` top-left on screen. Returns 0.
- A new window's **alpha is 0**: nothing shows until `SLSSetWindowAlpha(cid, wid, 1)`. Then `SLSSetWindowOpacity(cid, wid, false)` for a transparent background, `SLSSetWindowResolution(cid, wid, 2)` on Retina.
- Drawing: `SLWindowContextCreate(cid, wid, NULL)` gives a `CGContext` in points, origin bottom-left; draw, `CGContextFlush`, `SLSFlushWindowContentRegion(cid, wid, NULL)`.
- Resizing: `SLSSetWindowShape(cid, wid, 0, 0, region)`, then draw again into the same context at the new size. Verified.
- Click-through: `SLSSetWindowEventShape(cid, wid, CGRegionCreateEmptyRegion())`. Not verified on these windows; a `WALayerKitWindow` doesn't need it, see "A border drawn by Dock".
- `SLSOrderWindow(cid, wid, 1, 0)` shows it; `SLSReleaseWindow` removes it.
- `SLSSetMouseEventEnableFlag` is not exported on macOS 27.
- **Made in Dock, the same window is opaque black** wherever nothing is drawn (inside the stroke, outside the rounded corners); from a plain process, with or without AppKit, it is transparent. Not found why. A window made by a plain process stays transparent when Dock's connection moves and orders it (verified with `M` and `O` through the payload socket). Made by the daemon that way, two borders were on screen in the right place but showed nothing; left there.

### The outline around a hovered window in Mission Control

Read from Dock's disassembly and its Swift field metadata, build 26A5416b; nothing here was traced live. That this code is what shows on hover is inferred from the names (`ExposeHiliteLayerController`, the `hilite-windows-in-expose` preference).

- **It isn't a WindowServer feature.** SkyLight's exports have nothing matching hilite, highlight, outline, border, stroke or focus ring, and Dock imports nothing like it, so there is no call that outlines a window.
- **It is a plain `CALayer` of Dock's.** `ExposeHiliteLayerController`, a struct with one field `layer`, is made at `0x10015f4f8`: `borderColor` 0.188, 0.514, 0.984, 1 (`#3083FB`), `borderWidth` 5, `cornerCurve` continuous.
- **Placing it** (`0x10015f618`, the receiver a `WAWindow`): `systemFrame` outset by `borderWidth + 1.5`, through `convertRectFromGlobal:` and `convertRect:fromLayer:` into `setFrame:`. The radii are a field of the `WAWindow`, scaled by the thumbnail's width over the window's and grown by `borderWidth + 1.5`, into `setCornerRadii:`. A check not traced replaces them with 12. Where the field is filled wasn't traced either; `SLSWindowIteratorGetCornerRadii`, called in one place in Dock (`0x1002bdc68`), is the likely source.
- **It lives only in the overview's layers.** `UserSpaceController` and `ShowFrontWindowsController` each have a `_windowHighlight`, so there is nothing to switch on for a window on the desktop. `ShowFrontWindowsController` also has `_windowHighlightWindow`, a `WALayerKitWindow` made at `0x100280764` with tags `0x200` at `CGWindowLevelForKey(7)` (the Dock level), then `SLSTransactionAddWindowToSpace`.
- **`WALayerKitWindow` is how Dock gets a window out of layers:** a `WAWindow` subclass, `+[CAContext contextWithCGSConnection:options:]` (`0x1001927d8`), then `setLayer:` and `setColorSpace:` (`0x100192208`). It is the way around the opaque black windows above, see the next section.

### A border drawn by Dock

`probe/border.m`, a dylib loaded into the running Dock with `build/loader` (`make border-probe`), and `probe/follow.swift` for focus. macOS 27, build 26A5416b. Verified unless marked.

- **`WALayerKitWindow` works from an injected dylib, on Dock's main queue:** a `CALayer` with a border, added to `-layer`, gave a stroke around another app's window, fully transparent inside and outside it. In a screenshot of a 2× screen the stroke is exactly 5 pt of `#3083FB`, so the layer is in points.
- The init's types are in `__objc_methlist`, `otool -oV` prints them: `@72@0:8{CGRect}16I48I52f56Q60i68`, so connection `I`, display `I`, scale `f`, tags `Q`, level `i`. The display is a `CGDirectDisplayID`: it goes into `CGDisplayCopyColorSpace` at `0x100192264`. The connection is `SLSMainConnectionID()`: Dock's global at `0x100409ef8` read the same value live. `0x1002f0ba0` and the other callers' targets are `__objc_stubs`: on arm64e a stub is 32 bytes, its first two instructions load the selector.
- Inside the init: `SLSNewWindowWithOpaqueShapeAndContext` with an empty opaque shape, which is the likely difference from a black `SLSNewWindow` (inferred), `CGSSetWindowLevel`, the window property `CaptureOnlyEventRegion` = true, `CGSSetWindowResolution`. Tags get `0x0080000000801000` on top of what is passed. `setFrame:` is `SLSTransactionSetWindowShape` plus `SLSTransactionMoveWindowWithGroup`; it doesn't touch the layer, and it does nothing for an equal frame. `setFrame:with:` takes a transaction.
- **Clicks go through by themselves.** Real clicks (`cliclick`) with three panels logging `mouseDown`: on the target under the border, on the stroke, and on a window beside it, each reached the right panel at the right point, with an empty event shape and just as well with `SLSSetWindowEventShape` set to the whole window. So it isn't the event shape. `CaptureOnlyEventRegion` or tag `0x200` (`CGSTagTransparent` in old headers, from memory) is the likely reason; not separated.
- **Corner radius:** `SLSWindowQueryWindows(cid, wids, 0)`, `SLSWindowQueryResultCopyWindows`, `SLSWindowIteratorGetCornerRadii(iterator, index)` gives a +1 `CFArray` of four `CFNumber` doubles, the same value four times (all four read `+0x110`). It works from a plain process, for any app's window: 16 for Shepherd and Ardia, 28 for Telegram, 11.5 for TextEdit, 0 for a borderless panel. `cornerRadius` = window radius + `borderWidth` + gap runs the stroke parallel to the window's corner.
- **Stacking doesn't work: the border stays above every window of its level.** Level 0 and sublevel 0 like the others, and windows at a higher level (a floating panel, a PiP) do cover it, yet it stays above all level-0 windows, also ones above the target, also on being raised. Nothing moved it: `SLSOrderWindow` and `SLSTransactionOrderWindow` with order 1 or -1 relative to the target or to a neighbour, out and in again through `O`, `SLSTransactionOrderWindowGroup`, clearing every tag down to 0. The same `O` does move other apps' windows, under the border. From a plain process `SLSOrderWindow` on it returns 1000. Cause not found; that Dock's connection is special, or a window bound to a `CAContext`, are guesses. Not tried: `SLSSetWindowSubLevel`, a level below 0, and a second connection made in Dock.
  For the focused window this is mostly harmless, as it is usually the front one. It is wrong when something at level 0 lies over the focused window, a floating window above the strip for one.
- **It goes with its Space.** With `SLSMoveWindowsToManagedSpace` onto the target's Space, `SLSCopySpacesForWindows` lists that one Space, and with the overview open (scale 0.7) `CGWindowList` had it scaled and moved with the target: 220×150 at (601, −4260) around 211×141 at (605, −4256), the outset of 6.5 pt scaled too. Over about 4 minutes of the user's own work, polling both frames as drawn every 8 ms with the border following focus across 4 windows: the offset held at (−7, −7) in all 558 samples of Space slides, so the Space carries both, no lag. In the strip moves and resizes of the same log it was off in 426 of 1206 and 73 of 214 samples, by up to 108 pt, the polling below.
- **Following by polling is visibly late.** `SLSGetWindowBounds` on a timer of 8 ms: measured from outside, polling both frames as drawn at about 1 kHz, median 4 ms behind the target and up to 15 ms, for a payload `S` move and for a payload `R` stretch; commit method 1 or 4 made no difference. That is a frame now and then, and the user saw it at once. An `R` stretch doesn't show in `SLSGetWindowBounds` at all, so the border stood still until the app's resize; `CGWindowListCreateDescriptionFromArray` has it.
- **One transaction per frame isn't late at all.** The target's move or `SetWindowTransform3D` and the border's `setFrame:with:` in one `SLSTransaction`, the layer in a `CATransaction` around it: 0.0 ms at the median and at p90 over about 60 frames. Recorded with `screencapture -v`, the gap between target and stroke held at 3 px of a 2× screen through all 31 moving frames of a move, and 1–3 px through a stretch (rounding of the width), with commit method 0, 1 or 4 alike. So inside the payload's frame loop, where every move and stretch is computed, the border needs no polling. An app moving or resizing itself is not in that loop, and stays a frame late.
- **Groups don't cross connections.** `-[NSWindow addChildWindow:ordered:]` does `SLSTransactionAddWindowToWindowOrderingGroup(t, child, 1, parent)`, `SLSTransactionAddWindowToWindowMovementGroup(t, parent, child)` and `SLSTransactionOrderWindowGroup(t, child, 1, parent)`, traced in lldb. Done by hand in one process, moving the parent with `SLSTransactionMoveWindowWithGroup` moves the child by the same amount in that call. With the parent in another process nothing moves, from a plain process and from Dock alike, and no call reports an error. `SLSAddWindowToWindowOrderingGroup` and `SLSSetWindowParent` alone don't link movement even in one process. A parent's own `-setFrame:` doesn't move the child either, so a group would have covered only `MoveWindowWithGroup`.
- **The shadow is no way to draw it, as far as tried.** `SLSWindowSetShadowProperties(wid, dict)` with `com.apple.WindowShadow{Density,Radius,VerticalOffset,RimDensity,RimRadius,RimStyleHard,RimStyleWhite,InnerRim…}`, plain and with `Active`/`Inactive` suffixes, on a borderless panel of the same process: returns 0 and the shadow is simply gone, no rim either. Among the 40-odd such keys in the shared cache none is a color, only `RimStyleWhite` and `RimStyleHard`, so at best a black or white line (inferred). Not tried: a titled window, `SLSSetWindowShadowAndRimParameters`.
- **Another app's corner radius can't be set from Dock.** `SLSTransactionSetWindowCornerRadius(transaction, wid, double)` works on a connection's own windows: a titled `NSWindow` took 40 pt live, its shadow took the shape, and `SLSWindowIteratorGetCornerRadii` gave 40 (below the app's own radius its corners show against the clip; `SLSTransactionClearWindowCornerRadius` leaves 0, not what the window had). From Dock on Finder's window it does nothing: the getter still says 16, the picture is the same. `SLSTransactionSetWindowSystemCornerRadius`, which WindowManager imports, changed nothing either, on a process's own window or from Dock on Finder's, pixel for pixel along the corner's diagonal; `Clear…` after it too. WindowManager may hold something Dock doesn't (inferred). So nori has no such setting. The `NSConvolutionOverride1` default from the request wasn't found: two searches of the shared cache ran out of time, nothing was concluded; an app would read a default at launch anyway.
- The daemon's `listWindows` saw the border, a Dock window at layer 0: `nori query windows` listed it, with no column. `isStandard` kept it out of the strip since Dock's `AXWindows` don't have it. It now skips Dock's windows by owner name.

## Granting Accessibility (macOS 27)

- With Filesystem Protections off, root can write `kTCCServiceAccessibility` rows into `/Library/Application Support/com.apple.TCC/TCC.db` (schema version 36, journal mode `delete`). Rows aren't signed; the `integrity_flag` table is only `_sqlite3_integrity_check`'s result. Verified with an ad hoc signed probe app: `client` the bundle id, `client_type` 0, `auth_value` 2, `auth_reason` 4, `auth_version` 1, `flags` 0, `csreq` from `SecCodeCopyDesignatedRequirement` + `SecRequirementCopyData`, same as a row System Settings writes. Not tried with a Developer ID signature.
- `tccd` needs no restart. A new event tap and a fresh process saw the grant at once.
- **`AXIsProcessTrusted` in a running process does not.** It stayed false for 10 s and through a `tccd` restart, and a real Accessibility call right after the write failed with `kAXErrorAPIDisabled` (-25211). `hasAuthorizationForControlComputer` in HIServices caches the answer per pid and responsible pid, and `apiNotifyCallback` clears it on the distributed notification `com.apple.accessibility.api` (static reading). Posting that notification from the process itself, then running the run loop, flipped it in about 25 ms, both ways, and `AXUIElementCopyAttributeValue` on Finder went from -25211 to success. Verified.
- Once, after the probe's row was deleted, a row with `auth_value` 0 appeared for it; what wrote it wasn't traced. `INSERT OR REPLACE` overwrites such a row, the primary key being service, client, client type and indirect object.
- `tccutil reset All <bundle id>` gave OSStatus -10814 for the probe, also after `lsregister -f`, so removing that row takes root and sqlite3. `TCCAccessSetForBundle` wasn't tried: it should need `com.apple.private.tcc.manager`, which nori can't have.

## Loading the payload without a password (macOS 27)

- `task_for_pid` on Dock from a plain process, as the user, with Debugging Restrictions off. Verified with an arm64e probe that only asks for the port. Ad hoc signed, no entitlements: `KERN_FAILURE` (5) at once. With `com.apple.security.cs.debugger`: the call blocks, and `SecurityAgent` starts for the authorization right `system.privilege.taskport`, a password dialog. That right is `class user`, `group _developer`, `authenticate-user true`, `shared true`, `timeout 36000` (`security authorizationdb read system.privilege.taskport`), and `DevToolsSecurity -status` said Developer mode was disabled. So the entitlement only moves the password. Not tried: entering it, so whether the call then reaches Dock isn't known; `DevToolsSecurity -enable`, which should drop the prompt, but for every debugger of every `_developer` user. That Developer mode is what makes the lldb attach under "How to look" go without sudo is inferred.
- So the loader stays root, and root's part goes through sudo: `daemon/Loader.swift`. The rule names copies in a root-owned folder, not the files in the bundle. A bundle in /Applications belongs to the user, so a rule on it would let any process of theirs swap the file and run as root, and pinning it with a `sha256:` digest leaves a window between the check and the exec on a system without `fexecve` (from sudoers(5), as far as remembered; not tested).
- A rule with a numeric user, `#501 ALL=(root) NOPASSWD: …`, passes `visudo -cf` as a plain user, and the `#` doesn't make it a comment. It wins over the admin rule: verified with `sudo -n`, on an admin account whose `sudo -l` also lists `(ALL) ALL`. The same `sudo -n` refused, with "a password is required", `/bin/ls`, the loader with no argument or another dylib, and the bundle's own loader.
- A payload loaded from `/usr/local/libexec/nori` hooks like one from the bundle: all four `hooked (kr=0)`, the same bytes at another path. Verified with a Developer ID build; not tried ad hoc.
- **`sudo -n -l <command>` doesn't say a command runs without a password.** It answered yes, exit 0, for `/bin/ls`, which that account may only run with one. With any NOPASSWD rule in place listing needs no password (`listpw any`), and `-l` then reports what the user may run at all. So the daemon goes by the rule's file, which it can stat though not read.

## Our own Space animation: overview and switching

`step_layout` in `payload/payload.m`, command `Y spring target goal sid0 sid1 …`. The overview and a Space switch are one layout: the display's Spaces one under another, `focus` is the index at the center, `progress` 0 is normal Spaces, 1 is the overview (scale 0.4, gap 48). The payload moves it on every `CVDisplayLink` tick: the overview with a spring (response 0.4, damping 0.78, in real time), a switch like windows (a quarter of the remaining distance per frame). One transaction per frame: ShowSpace + a shape covering the whole display + SetSpaceTransform for every Space; the same transforms are handed to the hook in place of Dock's values.
At first the daemon computed frames on a `Timer` and sent one over the socket per frame — **it stuttered** (the timer isn't aligned with vsync, frames got lost or arrived in pairs). Space animations must live in the payload, like window animations.
Measured with 4 Spaces on a 60 Hz display (temporary counters in `step_layout`): no late ticks, a frame's work (ShowSpace + shape + transform for every Space, commit included) 0.1–0.2 ms on average and under 5 ms at worst. Re-committing the whole layout every frame is not what makes the overview stutter.

### Where the overview's stutter is (WindowServer, not the payload)

- **Measuring what reaches the screen:** `SLSGetPerformanceTotalUpdateCount(cid, uint64_t *count, uint64_t *other)` — the first value goes up by one per screen update WindowServer makes. Polled every 0.5 ms from any process, the intervals between changes are the real frame times (17 ms = 60 Hz). A screen recording (`screencapture -v`) is no good for this: encoding a 6K region loads the same GPU and Mission Control stuttered in it too.
- M1 Pro, one 6016×3384 display at 60 Hz, 4 Spaces, Option+O: the first 500 ms (the opening) gave 6–14 updates, median 39–46 ms, worst ~170 ms; the open overview at rest and the closing were at 17 ms. Mission Control opened the same way gave 24–25 updates, median 17 ms.
- Progress driven linearly 0 → 1 over 2 s with "G" (~120 updates possible): 1 Space in the layout 111, 2 Spaces 78, 4 Spaces 70. At progress 0–0.3, where about one Space is on screen, all three were alike. So it is **scaled Spaces on screen while their transform changes** that cost; at rest WindowServer keeps up even with every Space re-committed every frame.
- Not the cause: input timing (a layout run straight from the socket stutters the same), showing the Spaces earlier (the same with them shown off screen for a second before opening), the animated wallpaper (`WallpaperImageExtension` took 22–29% of the GPU even at idle, but stopping it changed nothing), any one window (Telegram, Shepherd, PiP at alpha 0 changed nothing).
- **It is the GPU, and it is the scale itself.** `sudo sample WindowServer` during the opening and in the open overview: the render thread sits in `semaphore_timedwait_trap` (waiting for the GPU), CPU 40–67% of one core; the stacks that do run are plain CA rendering (`CA::OGL::render_layers`, backdrop blurs for vibrancy windows, `create_surface_with_properties`). GPU "Device Utilization %" (`IORegistryEntry` `IOAccelerator` → `PerformanceStatistics`, no root needed) with the layout held through the socket at a fixed progress, screen 6016×3384 @ 60, a PiP video redrawing on the side, M1 Pro:

  | state (all at rest, step_layout committing every frame) | updates/s | GPU |
  |---|---|---|
  | no layout (the video alone) | 34 | 24% |
  | 4 Spaces, progress 0 (scale 1, only our commits) | 61 | 42% |
  | 4 Spaces, progress 0.002 (scale 0.999, same pixels) | 61 | 70% |
  | 4 Spaces, progress 0.5 (scale 0.7) | 64 | 65% |
  | 4 Spaces, progress 1 (scale 0.4, ~2.4 Spaces on screen) | 43 | 67%, gaps up to 85 ms |
  | 1 Space, progress 1 (scale 0.4) | 64 | 56% |
  | 4 on-screen windows at scale 0.999 by `SetWindowTransform3D`, no layout | 42 | 52% |
  | the same windows at scale 0.4 | 39 | 32% |

  A Space with any scale other than 1 costs about as much GPU as a full extra screen composite, and that does not shrink when the Space is drawn small: at 0.4 the overview's 2–3 visible Spaces don't fit in a 16.7 ms frame and the screen updates every 2–5 vsyncs. A translated Space (the slide, `ty` only) is at 60 Hz. A **window** transform costs in proportion to the pixels it draws (0.999 ≈ a full screen, 0.4 ≈ nothing), so Mission Control's way, windows scaled one by one and Spaces never scaled, is the cheap one.
- The first scaled frame is a hitch of its own: the layout held at progress 0 for 1.5 s (all Spaces shown) and then jumped to 1 gave a 109 ms gap on the first frame, then 50–70 ms ones. WindowServer sets the scaled path up (offscreen surfaces) when the scale first becomes non-1, however the Spaces were shown before.
- Side note from the same numbers: with the layout held settled, `step_layout` still commits every frame and WindowServer redraws the whole screen each time (61 updates/s against 34 with nothing going on). Harmless for the stutter, wasted work at rest.
- Measuring: `SLSGetPerformanceTotalUpdateCount` polled every 0.5 ms for the update rate and gaps; the IOAccelerator statistics for the GPU; `top -l N -s 1 -pid <WindowServer>` for its CPU (`proc_pid_rusage` on it needs root). The layout was driven straight through `/tmp/nori_$USER.socket` (`Q`, `Y 1 target 0 sids…`, then `G progress 0` to hold it) with the daemon stopped (`kill -STOP`) so the strip didn't act on transformed frames, and Option+O was pressed with `osascript … key code 31 using option down` when the real path was wanted.

### How Dock animates (static reading of Dock and SkyLight, macOS 27)

- Dock commits almost every transaction with `SLSTransactionCommitUsingMethod(t, 4)`. Methods 1/2 are `SLSTransactionCommit(t, 1/0)`; 3/4 go to `sls_transaction_commit_ca(t, bool)`, which puts the encoded transaction on the connection's fencing context (`SLSTransactionGetFencingContext`, `setPayload:`), so it lands in WindowServer with Core Animation's commit, in the same frame as Dock's layer changes.
- No `CVDisplayLink` in Dock: dispatch timers and `SLSDisplayGetTiming`. It also calls `SLSTransactionSetManagedDisplayIsAnimating` around its animations.
- Mission Control is Core Animation in Dock's own `CAContext`: `CAPortalLayer` (live window content), `CASpringAnimation`, and snapshots for windows on other Spaces (log string "Returning snapshot-backed miniLayer for window %x on space %s"). It never scales whole Spaces.
- `SLSTransactionSetSpaceTransform`'s `u32` is only encoded and sent; what WindowServer does with it is not known. `SLSTransactionSetWindowResolution` is used by Dock only when it creates its own windows.

### Sticky windows (on every Space)

A window with `canJoinAllSpaces` (a status bar, JankyBorders, PiP) is listed on every Space by `SLSCopySpacesForWindows(cid, 7, [wid])`, but WindowServer draws it with **one** Space's transform.
- Dock's own slide (hooks off, macOS 27): it slides out with the old Space and appears on the new one only when the switch ends. Verified on a screen recording, with the status bar and with a test window (`canJoinAllSpaces | stationary`, floating level). Dock does nothing to keep them in place, so there is nothing to copy from it.
- `CGWindowListCopyWindowInfo` reports their frame with that Space's transform applied (and with a window transform, if any).
- Holding them in place: a window transform that undoes the Space transform. For a Space transform `t` (screen → Space, `a = d`, `b = c = 0`) and a window at origin `o`: `m11 = 1/a`, `m22 = 1/d`, `m41 = ⌊(⌊o.x⌋ − tx)/a + 1/256⌋ − ⌊o.x⌋`, `m42 = ⌊(⌊o.y⌋ − ty)/d + 1/256⌋ − ⌊o.y⌋`, the rest identity. Verified with the overview open (a = 2.5): the test window was back at its own place and size, drawn over the overview. For the floors, see below.
- **Which Space: the one that last went from hidden to shown**, and they stay with it while it is shown. `ShowSpace` on a Space already shown changes nothing; `HideSpace` + `ShowSpace` in one transaction counts as becoming shown and doesn't blink. Verified with the overview through the payload socket (current Space 157, list `5 157 165 180`): opened on 5 or 165 (hidden before) the status bar stayed put; opened on 157 it went with 5, the last of the others to become shown; with hide + show of the target every frame it stayed put in all of these.
- **Except during Dock's own switch** (from its first frame until the current Space changes): then they go with the current Space, whatever was shown last. That is why they slide out with the old Space in Dock's slide. Seen: with the target held, the status bar sat a screen away (y = −1692) from the end of our slide until `SLSGetActiveSpace` turned to the target, about 250 ms.
- A fractional slide made them shake by about a pixel; a whole-point `ty` doesn't.
- **WindowServer draws a window of a transformed Space from a whole point: `⌊(⌊o⌋ − t)/a + 1/256⌋` on each axis.** The window transform's own translation is kept exactly, so the exact undo (`(o − t)/a − o`) left the window off by the fraction dropped, up to 1 pt up and left. Content is resampled at that offset, so it blurs too, and as the fraction changes every frame of an overview animation the window shakes. Verified by holding the overview at fixed progress with `G` and `F`: the displacement equals `−frac(m41)`, `−frac(m42)` within 0.05 pt, for the status bar and for test panels at three origins. Floored as above, a test panel matched its plain frame with zero difference: scale 0.4–0.94, Space moved so that the position is negative, whole and half-point origins. `round` is 1 pt off half the time. Plain `⌊(o − t)/a⌋ − o` is right for a whole `o` but not a half-point one. Double rounding is no issue at rest: at progress 1, `a = 2.5` and `tx`, `ty` are exact (checked over every origin on a 3008×1692 screen). The floor of `o` also makes the undo exactly zero for an identity Space, so a window's transform clears when the layout ends.
- The 1/256: a position just under a whole point counts as that point. Measured at scale ≈ 0.4 on a panel with a whole position of 822: up to 3.8/1000 below, WindowServer used 822; from 4/1000 below, 821. So the limit is between those, most likely 1/256, a fixed-point fraction (inferred). It matters: a 3-finger swipe in the overview keeps `layout_progress` a hair under 1, the spring never quite settles, and a window whose position is whole at rest (x = −1 at scale 0.4: 902) fell 1 pt on some frames without it. Measured on one 2× screen; not checked at 1×.
- How to test a window transform by hand: a held window is rewritten every frame, but `find_sticky` skips a window whose center is off the layout's display. So a sticky panel 300 wide at x = −200 is left alone, stays under the Space transform, and takes `D` lines, with 100 pt of it on screen to measure. A panel opened after the layout began won't do: it was drawn with no Space transform at all (cause unknown). Offsets: a panel of fixed noise, the mean absolute difference from its plain capture, searched over ±8 px at 2× (`screencapture -R`); edges of a solid panel mislead, as they snap to pixels while the content doesn't.
- Strip moves don't touch the status bar: recorded during `nori focus left/right`, it was at offset 0 in every frame, as during a plain `nori focus space N`, apart from the bar redrawing its own Space indicator.
- In the payload: `held_space()` is the target, or the current Space from Dock's first frame until `SLSGetActiveSpace` answers the Space Dock made current; `step_layout` hides and shows it again after the others every frame, and the `SetSpaceTransform` hook undoes its transform, in our transactions and in Dock's. Sticky windows are listed when a layout starts and added to on every `Y` (on screen, layer ≥ 0, on more than one Space or on one with the sticky tag, centered on the layout's display); their origins are re-read every frame.
- `SLSGetWindowBounds` gives a window's own frame: no Space transform, no window transform. Verified in the overview: a held status bar and an unheld sticky window both came back with their real frames, while `CGWindowListCopyWindowInfo` had the unheld one scaled and moved.
- JankyBorders' border windows are each on one Space, the one of the window they frame (five of them, all on the current Space, `SLSCopySpacesForWindows`), so they slide with it and are not held.
- Wrong turns, for the record: undoing whichever Space a transaction transforms last (they shook: Dock's frames transform both Spaces and show nothing); showing the target last without hiding it (they stayed with another Space when the target was already shown); a larger `SetSpaceShape` (changed nothing); skipping Dock's `SetSafeApertureSpaceReveal` (changed nothing).
- `SLSTransactionSetSafeApertureSpaceReveal(transaction, sid, double)`: Dock calls it every frame of its switch for both Spaces, the old one going 1 → 0, the new one 0 → 1 (logged). Prologue `pacibsp; stp d9,d8,[sp,#-0x30]!; stp x20,x19,[sp,#0x10]; stp x29,x30,[sp,#0x20]`.
- **The sticky windows still vanish for the ~200 ms between the end of our slide and the Space change** (held = the current Space then, its undo in place), and with them the status bar "cut off" and PiP "blinking" on a switch. Traced on a screen recording (`screencapture -v`, 30 fps, split with ffmpeg) with a diagnostic factor on the undo during `dock_switching`: the bar is in the on-screen window list the whole time, alpha 1, reported at its place, so neither the app nor the model hides it. Undo × 1.5 (the bar lands at y = 0.5 × height): **drawn, on top of the new Space** — so both the Space transform and the window transform apply and nothing covers it. Undo × 1.06 (y ≈ 100 pt): drawn, during the whole slide. Undo × 1.02 (y ≈ 34) and × 1 (y = 0): gone. So during Dock's own switch a top band of the current Space, somewhere between 68 and 100 pt tall, is not drawn, and the sticky windows in it go with it: the status bar (0–34) entirely, the PiP (from y 68) its top. **The band is the system menu bar, window level 24**, drawn over the top of the screen for the whole of Dock's switch even though it is auto-hidden (`_HIHideMenuBar`; transparent on macOS 27, so the wallpaper shows through it). Shown with three sticky, stationary test windows 34 pt tall at y = 0 (`canJoinAllSpaces | stationary`): level 23 (the status bar's) is gone for the usual 6–7 frames, levels 25 and 1000 stay, except for one frame right at the Space change (the handoff of the sticky windows to the new Space; that single frame is the PiP's "blink"). Not it, each hooked the same way as the Space transform and checked on a recording: `SetSafeApertureSpaceReveal` forced to 1 or to 0 for the layout's Spaces (its third argument is a double, `frintm d0, d8` in the prologue), and `SLSTransactionSetMenuBarSystemOverrideAlpha(transaction, id, float)`, which Dock doesn't even call during a switch; `CGWindowListCopyWindowInfo` doesn't list the menu bar window either. So the undo transform is right and nothing in the payload can lift the sticky windows above the menu bar; a status bar wants level ≥ 25 (`NSStatusWindowLevel`), and a PiP at level 3 keeps losing its top band for those frames. (Later: narrow panels at levels 3 and 26 lost nothing once the current-Space change was handled, see below; what still took the bar out at level 25 was its full width.)
- **A window spanning the top edge of the screen from side to side is hidden during Dock's switch, whatever its level.** That is what kept taking the status bar out (7–15 frames per switch, from the middle of the slide), long after it moved to level 25. Recorded with sticky test panels 34 pt tall (`canJoinAllSpaces`), one at a time, on normal switches: full width at y = 0, level 26: gone for 10 frames, like the bar; 3000 wide at x = 4, y = 0: none lost; full width at y = 2: none lost; full width 1 pt above the screen (y = −1, 35 tall): none lost; 1 pt past both sides (x = −1, 3010 wide): none lost. So it is the frame, not the app or the level: a full-width status bar wants to be 1 pt wider than the screen on each side (or 1 pt taller, above it). Nothing in the payload changes this; it goes by the window's frame.
- **The last frame lost by every sticky window was the current-Space change**, which mostly falls in the middle of our slide (motion in frames 91–103, the change at 98 or 99). Dock makes the target current with `SLSTransactionSetManagedDisplayCurrentSpace(transaction, CFStringRef display uuid, uint64_t sid)` (prologue `pacibsp; stp x22,x21,[sp,#-0x30]!; stp x20,x19,[sp,#0x10]; stp x29,x30,[sp,#0x20]`). The windows go over to the new current Space when that transaction is committed, but `SLSGetActiveSpace` answers the old one until then, so the undo set in the same transaction (the `SetSpaceTransform` hook) was the old Space's: one frame off screen, until the next `step_layout`. The payload hooks it (`nori_current_space`): the new Space's undo goes into that transaction, and `held_space()` uses that Space from then on. After that: four switches, up and down, with a level-26 panel at y = 0 and a level-3 one at y = 40 (where a PiP sits): no frame lost. This held only while Dock's `HideSpace` passed; see below for what replaced it.
- **Space switches inside the overview need Dock's hide of the old Space dropped, and then the undo must not move with the change.** The overview shows the old Space all along, and Dock hides it in its last transaction, so the old Space was gone until the next `step_layout` showed it again: a one-frame blink, when the two fell on different frames (seen about once in 8 switches, in a recording of the whole screen). The payload hooks `SLSTransactionHideSpace` (`nori_hide_space`, prologue `pacibsp; stp x20,x19,[sp,#-0x20]!; stp x29,x30,[sp,#0x10]; add x29,sp,#0x10`) and drops the hide for a Space the layout shows; `step_layout` calls it too, with `in_step_layout` set, so the layout still hides what it should at its end. With the old Space kept, **the sticky windows stay on it after the change is committed**, so undoing the new Space in Dock's transaction left them a Space step off for 1–2 frames, as the next `step_layout` comes 25–30 ms after the change. Tried over 16 switches each, panel frames lost: Dock's hide passes, 0 (and the Spaces blink); hide dropped, 9; dropped, plus hide + show of the target in the hook of the change, 12; hide passing plus show of the old Space and hide + show of the target in its place, 9; dropped, plus hide + show of the target in its place, 16. All of those run before the change itself, last in the transaction, which is the likely reason they did nothing (inferred). What works is doing nothing at the change: the undo stays with the old Space until `SLSGetActiveSpace` answers the new one, and then one `step_layout` hides and shows the target and undoes it in a single transaction. Result: 32 switches, 8 of them 260 ms apart: no frame lost by the status bar or a level-25 panel, and no Space blink.
- The overview is one layout through many switches, so the state of a Dock switch can't live as long as the layout. It used to, and from the second switch on the windows were undone for the old Space from the key press to Dock's first frame, 50–430 ms later: a Space step off, or off the top of the screen. Clearing it on every `Y` wasn't enough either: normal-paced switches came clean, rapid presses still lost 17 frames (why wasn't traced). It ends when the change is committed now, and rapid presses lose none. Dock's frames run right up to the change: 18 frames over about 300 ms, the last one within 10 ms of it.
- How this was found, for next time: a temporary payload with a ring buffer of timestamped hook calls and the variants behind a socket line, so one Dock reload (which takes the sudo password) covers every variant. Lost frames: record the screen with `screencapture -v`, open a sticky noise panel first, and search each frame for it and for the bar. - Also in place, not seen to matter on its own because the change comes before our slide ends: once our slide is over and Dock's switch isn't, the old Space is put where the target is (under it), so that a late change goes between two untransformed Spaces.

- **`SLSGetWindowBounds` leaves window transforms out, and shows an app's resize the frame it lands.** Own test window: 600 wide under a 1.5× stretch (`SetWindowTransform3D`), 900 about 12 ms after `-setFrame:` to 900. The width stretch ("R") now drops itself when the window's own width reaches the goal, checked every millisecond while it waits for the app, instead of waiting for "W", which comes an AX round trip later: each frame between was drawn stretched twice.
- **Dock hides the Space it leaves in the transaction that ends its switch, and entering a fullscreen Space it hides every Desktop.** Mid-layout that blanked them for a frame until `step_layout` showed them again: in the overview, one sample (~8 ms) with the old Space's windows, or every Desktop's, missing from the on-screen list. The payload hooks `SLSTransactionHideSpace(transaction, sid)` (prologue `pacibsp; stp x20,x19,[sp,#-0x20]!; stp x29,x30,[sp,#0x10]; add x29,sp,#0x10`, `d503237f a9be4ff4 a9017bfd 910043fd`) and drops Dock's hides of the layout's Spaces while it runs; its own hides go through. Not yet verified live.

The daemon (`daemon/Overview.swift`) intercepts every "Switch to Desktop N" in the event tap (from `com.apple.symbolichotkeys`, read at start), sends `Y`, then `V` so that Dock changes the current Space. Where the payload didn't find Dock's code, or isn't there, it presses the same shortcut again instead (it lets its own press through by the `passDesktopHotkeys` counter). The layout finishes only once it is back at progress 0 and `SLSGetActiveSpace` is the target Space (or after 1 s): then the target Space has no transform, the others are hidden, and the hooks let Dock through again.

### Something behind the overview's Spaces

Between and around the scaled Spaces the screen is black: nothing is below them. A window can't go there by itself: a Space is composited as one layer, so even a window at the lowest level, sticky or not, is drawn with its Space (a sticky one with the held Space, on top of the others). Inferred from the sticky-window findings above, not tried.
- **A Space of our own at a negative absolute level is.** From the daemon's connection, no Dock needed: `CGSSpaceCreate(cid, 1, 0)`, `CGSSpaceSetAbsoluteLevel(cid, sid, -1)`, `CGSSpaceAddWindowsAndRemoveFromSpaces(cid, sid, [wid], 7)`, then `CGSShowSpaces`/`CGSHideSpaces(cid, [sid])` to show or hide it. The desktops are at absolute level 0 (`CGSSpaceGetAbsoluteLevel`). Verified with a full-screen red window and the overview open: at level 0 it covered every Space's wallpaper (drawn above it, below the apps' windows); at -1 and at -1000 it was only around the Spaces, wallpapers whole.
- The window there is on screen only while its Space is shown (`CGWindowListCopyWindowInfo` on-screen lists it then, not after `HideSpaces`), and `CopySpacesForWindows` gives just that Space, so the payload's sticky list leaves it alone. At layer 0 it would look like an app window to anything that lists them; at the desktop level it doesn't, and in a Space of its own the level changes nothing on screen.
- This is `overview-background = "blur"` (`showBackdrop` in `daemon/Overview.swift`).

## Payload → daemon

The payload reports back on the daemon's control socket (`/tmp/nori-ctl_$USER.socket`, the one `nori query/focus` uses), one request per connection, tab-separated: `payload<TAB>layout-done<TAB><seq>` when a Space layout ends (seq from the `Q` line sent before its `Y`, so an older layout's end doesn't unpause a newer one) and `payload<TAB>resize-settled<TAB><wid><TAB><width>` when a width stretch reaches its goal. The daemon unpauses the strip and runs the app's AX resize on these instead of fixed delays; the delays (3 s, 0.8 s) stay only as fallbacks. The payload reads the (empty) reply to EOF before closing, so the daemon never writes to a closed socket. Not yet verified live.

After every `P` the payload also sends `payload<TAB>hooks<TAB><names>`, the hooks that didn't go in, comma-separated, empty when all did. On every `P` and not once: the first `P` of a daemon can reach the payload before that daemon listens on its control socket, and a dropped report would never come again.

### What a missing hook costs

From reading `payload/payload.m`, not from running without one. `step_layout` itself calls all these functions, so with the hooks gone the overview still opens, scales and closes; what goes is the part that needs to see Dock's calls.

- `SLSTransactionSetSpaceTransform` (`nori_space_transform`): the most costly. `hold_sticky` is called only from here, so windows on every Space aren't held: they move and scale with one Space, also in `step_layout`'s own frames. Dock's frames keep their values, so a switch has Dock's horizontal transforms landing between `step_layout`'s. A switch outside a layout stays horizontal, and `I 1` does nothing here.
- `SLSTransactionSetSpaceShape` (`nori_space_shape`): Dock's clip stays. That is the black band of a slide made vertical with a horizontal clip (see "Space switching in Dock"). `step_layout` sets a full clip again each frame, so inside a layout it should only show on frames where Dock's transaction lands after ours (inferred).
- `SLSTransactionSetManagedDisplayCurrentSpace` (`nori_current_space`): `dock_current` stays 0, so `dock_switching` doesn't end until the next layout. A plain switch loses nothing, as the layout ends there. The overview is one layout through many switches: from the second on, sticky windows are undone for the old Space until Dock's first frame, a Space step off, the fault described under "The overview is one layout through many switches".
- `SLSTransactionHideSpace` (`nori_hide_space`): Dock's hides of the layout's Spaces pass, so in the overview the Space a switch leaves, or every Desktop when entering a fullscreen Space, blinks for a frame until the next `step_layout`.

`SLSTransactionSetManagedDisplayCurrentSpace` is the only one looked up with `dlsym`. The payload links the other three by name, along with the rest of its SkyLight calls (`nm -u build/payload.dylib`), so a SkyLight without one of those should fail the whole `dlopen` in Dock (inferred): then the loader finishes, Dock doesn't answer, and nori says so at launch.
